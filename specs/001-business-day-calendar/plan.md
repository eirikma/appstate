# Implementation Plan: Business Day Calendar

**Branch**: `001-business-day-calendar` | **Date**: 2026-02-14 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/001-business-day-calendar/spec.md`

## Summary

A calendar module that stores dates tagged by multiple tag-sets
(weekend/workday, Christian holidays, Norwegian red calendar days).
Tag-sets declare dependencies; tagging services execute in topological
order when populating a month. The module exposes query interfaces for
date-range and tag-set-filtered lookups. Persistence is abstracted
behind a repository interface with a default JDBC implementation.
Schema is managed by module-owned Liquibase changeLogs.

## Technical Context

**Language/Version**: Java 25
**Primary Dependencies**: Spring Boot (customizer beans), Liquibase
(schema management), JDBC (default repository implementation)
**Storage**: PostgreSQL via repository abstraction; module owns its
Liquibase changeLog
**Testing**: JUnit 6 + JSpec (unit tests), Testcontainers PostgreSQL 17
(integration tests via tests-common module)
**Target Platform**: JVM library module (consumed by other modules)
**Project Type**: Maven multi-module
**Performance Goals**: Library - no specific latency targets; correctness
over performance
**Constraints**: Immutable domain model (records), no `var`, functional
style preferred
**Scale/Scope**: Calendar dates for practical business date ranges
(years to decades)

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

### I. Immutable by Default — PASS

- CalendarDate, Tag, TagSet: Java records (immutable by construction).
- Query results: returned as unmodifiable collections.
- TaggingService.tag(): receives read-only view of existing tags,
  returns new immutable map.
- No mutable state in domain model.

### II. Test-Driven Development — PASS

- TDD cycle enforced for all behavioural changes.
- Unit tests: JUnit 6 + JSpec for domain logic (Computus, tagging
  services, dependency resolution).
- Integration tests: Testcontainers PostgreSQL 17 for repository
  and end-to-end population/query flows.
- tests-common module provides shared infrastructure.

### III. Incremental Change — PASS

- Task breakdown follows Expand-Migrate-Contract pattern.
- Each task produces compilable code with passing tests.
- Infrastructure (repository interface) added before implementations.
- Built-in tag-sets added one at a time, each independently testable.

### IV. Single Responsibility — PASS

- TaggingService: one per tag-set, single concern (tagging).
- CalendarPopulator: orchestrates population only.
- CalendarQuery: read-only query only.
- CalendarRepository: persistence only.
- TagSetRegistry: registration and dependency resolution only.
- DependencyResolver (Kahn's algorithm): topological sort only.

### V. Simplicity — PASS

- Repository pattern: justified by FR-001 (explicit requirement for
  storage abstraction).
- Kahn's algorithm: simplest correct topological sort with built-in
  cycle detection.
- Plain JDBC over JPA/Hibernate: simpler, aligns with immutable records.
- No speculative abstractions.

### Post-Design Re-Check — PASS

All five principles remain satisfied after Phase 1 design. No
complexity violations to justify.

**Structure Decision**: Maven multi-module with three new modules:
`business-day-calendar` (domain + default JDBC impl),
`tests-common` (shared test infrastructure), and
`business-day-calendar-integration-tests` (integration tests separated
from the main module to avoid testcontainer dependency in production
code). The integration tests module depends on both
`business-day-calendar` and `tests-common`.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|--------------------------------------|
| Repository pattern | FR-001 requires storage abstraction | Direct DB access would couple module to PostgreSQL |
| Separate integration-tests module | Keeps testcontainer/Liquibase dependencies out of production classpath | Single module would leak test infrastructure to consumers |
